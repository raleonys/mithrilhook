# Relocated x87 environment save exposes the trampoline address

## Review status

This is a report-only review. It does not change the runtime engine. The
finding was reproduced against `04d422258afe7958dc64392263d5810b0d9c50b1`,
the merge commit of PR #18 and current `master` at the time of review.

## Finding

MithrilHook refuses the known relative CALL-next get-PC idiom because moving
the CALL changes the address observed by the program. The x87 environment has
another architectural instruction-pointer observation path. An x87 operation
updates the saved FPU instruction pointer, and `FNSTENV` stores that pointer in
the caller's buffer. If both instructions are copied, the published original
stores the trampoline address instead of the source address.

The following leaf function uses the Windows x64 first-argument register and
contains no overlapping instructions:

```text
00: d9 ee       fldz
02: d9 31       fnstenv [rcx]
04: dd d8       fstp st(0)
06: c3          ret
```

The relocator copies six bytes before its jump-back. Hook creation therefore
accepts and publishes a trampoline containing all three x87 instructions.
`FNSTENV` stores the low 32 bits of the preceding `FLDZ` address in this mode;
moving `FLDZ` changes that observable value.

## Independent observations

A public-API probe compiled the complete current engine with the diagnostic
Win32 projection, used GCC's `ms_abi` for the Windows x64 RCX calling
convention, and executed the generated code on the host x64 CPU. It produced:

```text
create=MTH_OK enable=MTH_OK
target=0x7f40084de000 original=0x7f40084c0f00
source saved FIP=0x084de000
original saved FIP=0x084c0f00
environment buffers equal=0
disable=MTH_OK shutdown=MTH_OK
PROJECTED_RUNTIME_TABLES_REMAINING=0
```

The complete 28-byte environment buffers differed only in the saved
instruction-pointer field for this bounded case. The target source was restored
and every projected runtime table was retired, isolating the failure to the
published original's instruction semantics rather than cleanup ownership.

This candidate was first selected by a deterministic differential run over
250,000 generated byte programs. Of these, 189,405 decoded independently and
169,102 were accepted by the production relocator. After straight-line
completion filtering, complete memory reset and full CPU-context reset, 41,797
accepted source programs completed: 41,796 matched exactly and this x87 FIP
case was the sole mismatch. The minimal case was then reduced and reproduced
independently through the public API as above; the random run is discovery
evidence, not the acceptance claim.

## Scope

This is not the documented limitation that an ordinary relocated CALL can
expose a different return address to its callee. No CALL is present. It is also
not a decoder-length, overlapping-instruction, unwind-registration or target
lifetime failure. The x87 environment explicitly publishes the relocated
instruction address as data.

`FSTENV`, `FNSAVE`/`FSAVE`, `FXSAVE` and extended state-save forms can carry
related x87 instruction-pointer state and need an explicit policy review. A
save may also occur later in the source body after a copied x87 operation, so
checking only an environment-save instruction inside the stolen prefix may not
establish general preservation.

## Expected correction and acceptance

The engine must not publish an original while claiming preserved execution for
a copied sequence whose architectural x87 instruction pointer is observably
changed. A bounded, proven transformation is acceptable; otherwise creation
should conservatively return `MTH_ERROR_UNSUPPORTED_FUNCTION` without
publishing `ppOriginal` or changing target bytes.

Acceptance should include genuine Windows x64 public-API execution of the exact
RCX fixture above before enable, through the enabled target, through the
original path and after disable. It should verify the stored FIP field, target
bytes, x87 stack balance, original publication, runtime-table ownership and
retirement. Negative controls should prove the old accepted/different behavior
fails, and the review should explicitly classify wait/non-wait environment and
state-save variants plus a save occurring after the copied prefix.
